# S3 (Simple Storage Service)

- Durability: 99.999999999% (11 nines) across multiple AZs for **every** storage class; availability (how readily accessible the service is) varies by class — e.g. Standard's 99.99% availability equals about 53 minutes of downtime/year
- Best practices: enable versioning and MFA Delete
- Use cases: backup/storage, disaster recovery, archive, hybrid cloud storage, application/media hosting, data lakes & big data analytics, software delivery, static websites

## Buckets & Objects

- Buckets are defined at the region level (S3 looks global, but each bucket lives in one region)
- Bucket naming: globally unique across all accounts/regions (shared global namespace) OR reusable per-region under the newer account-regional namespace; no uppercase, no underscores, not formatted as an IP, must start with a lowercase letter or number, must not start with `xn--` or end with `-s3alias`
- Objects: the "key" is the full path (prefix + object name) — there's no real concept of directories, just long keys containing `/`; max object size 50TB; must use multi-part upload above 5GB (recommended above 100MB); objects can carry system/user metadata, up to 10 tags, and a version ID if versioning is enabled

## Lifecycle Actions

- **Transition actions** — move objects to a cheaper storage class after N days, e.g. Standard → Standard-IA after 60 days, or Standard-IA → Glacier for archiving after 6 months
- **Expiration actions** — delete objects after N days, e.g. expire access log files after 365 days; also used to delete old/noncurrent object versions (if versioning is enabled) or incomplete multi-part uploads
- 30-day minimum before a lifecycle policy takes effect
- Can scope rules to a prefix (e.g. `s3://mybucket/mp3/*`) or an object tag (e.g. `Department: Finance`)
- S3 Storage Class Analysis: recommends when to transition objects to Standard-IA (does not support One Zone-IA or Glacier); daily report, 24-48h to start showing data — good starting point before writing/improving Lifecycle Rules

## Storage Tiers

- Move between classes manually or via Lifecycle Rules
- **Standard** — general-purpose, 99.99% availability, no retrieval fees or minimum storage duration
- **Standard-Infrequent Access** — infrequent access, replicated across multiple AZs, 99.9% availability, for DR/backups
- **One Zone-Infrequent Access** — infrequent access, single AZ (cheaper, less durable — data lost if the AZ is destroyed), 99.5% availability, for recreatable data or secondary backup copies
- **S3 Express One Zone** — single-AZ, up to 10x faster / 50% cheaper than Standard, single-digit ms latency at 100,000s requests/sec, objects live in a "Directory Bucket"; best for latency-sensitive/AI-ML training/HPC workloads co-located with compute in the same AZ
- **Glacier Instant Retrieval** — millisecond retrieval, good for data accessed ~once a quarter; 90-day minimum storage duration; see [glacier.md](glacier.md)
- **Glacier Flexible Retrieval** — Expedited (1-5 min), Standard (3-5h), or Bulk (5-12h, free) retrieval; 90-day minimum storage duration; see [glacier.md](glacier.md)
- **Glacier Deep Archive** — long-term storage; Standard (12h) or Bulk (48h) retrieval; 180-day minimum storage duration; see [glacier.md](glacier.md)
- **Intelligent Tiering** — automatic cost optimization based on access patterns; small monitoring/auto-tiering fee, no retrieval charges, auto-moves objects between Frequent/Infrequent (30 days)/Archive Instant (90 days) tiers automatically, plus optional Archive/Deep Archive tiers on a configurable schedule

## Versioning

- Versioning is bucket-level; overwriting the same key creates new numbered versions; objects that existed before versioning was enabled show version `null`; suspending versioning does not delete prior versions
- **MFA Delete** — requires versioning; required to permanently delete an object version or suspend versioning; NOT required to enable versioning or list deleted versions; only the bucket owner (root) can toggle it
- **S3 Object Lock** — requires versioning; blocks version deletion for a set time (WORM model)
  - Compliance mode: nobody, including root, can overwrite/delete/shorten the retention
  - Governance mode: most users can't overwrite/delete, but specific users can be granted permission
  - Retention Period (fixed, extendable) is separate from Legal Hold (indefinite, freely added/removed via `s3:PutObjectLegalHold`)

## Replication

- Replication (CRR & SRR): both source and destination buckets must have versioning enabled; replication is async and requires IAM permissions; only new objects replicate by default (use S3 Batch Replication to backfill existing/failed objects); delete markers can optionally replicate, but version-specific deletes never do (prevents malicious deletion); replication does not chain (bucket1→bucket2→bucket3 does not propagate bucket1's objects to bucket3)
- CRR use cases: compliance, lower-latency access, cross-account replication
- SRR use cases: log aggregation, prod/test replica sync

## Batch Operations

- Run one job (list of objects + action + params) across existing objects: modify metadata/tags/ACLs, copy between buckets, encrypt unencrypted objects, restore from Glacier, or invoke a Lambda per object
- Handles retries, progress tracking, completion notifications, and reports; pair with S3 Inventory + Athena to build the object list

## Access Control

- Prefer IAM policies over bucket ACLs (older, less flexible, can be disabled); Bucket Policies are resource-based JSON (Effect/Principal/Action/Resource) set from the console and support cross-account access
- An IAM principal can access an object if either the IAM policy OR the resource (bucket) policy allows it, AND there's no explicit Deny — an explicit IAM **Deny** always overrides any other Allow (IAM policy, bucket policy, or ACL) the user has to access an S3 resource
- Block Public Access settings (account- or bucket-level) override any ACL/policy-granted public access — exist specifically to prevent data leaks
- **Pre-signed URLs** — generated via Console (1 min–12h), CLI (`--expires-in`, default 3600s, max 604800s/168h), or SDK; inherit the permissions of whoever generated them; useful for temporary GET/PUT access (premium downloads, dynamic user file lists, scoped upload locations)
- **Multi-part upload** for large files
- **Requester Pays** — shifts the request/data-transfer cost to the requester instead of the bucket owner; useful for sharing large public datasets; requester must be an authenticated AWS principal (no anonymous requests)

## Access Points & Object Lambda

- **S3 Access Points** — per-use-case named access to a bucket, each with its own DNS name and an access-point policy; a VPC-origin access point requires a VPC Endpoint (Gateway or Interface) whose policy also allows the bucket/access point
- **S3 Object Lambda** — runs a Lambda to transform an object on the way out (via an Object Lambda Access Point) without duplicating data; use cases: redacting PII, format conversion (XML→JSON), on-the-fly image resizing/watermarking

## Encryption

- 4 methods for encryption at rest: **SSE-S3** (AES-256, AWS-owned keys, default for new buckets/objects, header `x-amz-server-side-encryption: AES256`), **SSE-KMS** (customer-controlled KMS key with CloudTrail audit trail, header `aws:kms`, but upload/download calls count against KMS's per-second quota — request a quota increase if needed), **SSE-C** (customer-fully-managed key, S3 never stores it, HTTPS mandatory, key passed in every request header), and **Client-Side Encryption** (customer encrypts/decrypts before ever hitting S3)
- Encryption in transit = SSL/TLS via the HTTPS endpoint (vs. the unencrypted HTTP endpoint); can force it with a bucket policy checking `aws:SecureTransport: false` → Deny; bucket policies are evaluated before default (SSE-S3) encryption, so you can also force PUTs to include SSE-KMS/SSE-C headers

## CORS

- Cross-Origin Resource Sharing controls whether a browser lets a request from one origin (scheme+host+port) reach another; configure `Access-Control-Allow-Origin` on the bucket to allow specific origins or `*`

## Event Notifications

- Trigger on `ObjectCreated`, `ObjectRemoved`, `ObjectRestore`, `Replication`, etc., with optional filename filtering (e.g. `*.jpg`); typically deliver in seconds
- Can also route through **Amazon EventBridge** for JSON-rule filtering (by metadata/size/name) and multiple destinations (Step Functions, Kinesis Streams/Firehose) with archive/replay/reliable-delivery capabilities

## Performance

- Auto-scales to ~3,500 PUT/COPY/POST/DELETE or ~5,500 GET/HEAD requests/sec *per prefix*, with no cap on the number of prefixes — spreading reads across prefixes multiplies effective throughput
- **Byte-Range Fetches** let you parallelize/resiliently retrieve partial objects
- **S3 Transfer Acceleration** — routes uploads to the nearest AWS edge location, which forwards to the target-region bucket; compatible with multi-part upload

## Monitoring & Logging

- **S3 Access Logs** — logs every request (any account, authorized or denied) to a separate target bucket in the *same region*; never point the logging bucket at itself (creates an infinite logging loop)
- **S3 Storage Lens** — org-wide storage analytics (30 days of usage/activity by default), aggregable by org/account/region/bucket/prefix, with default or custom dashboards, and optional daily metric export to S3 (CSV/Parquet); free tier gives ~28 metrics for 14 days, paid tier adds activity/cost/data-protection/status-code metrics, CloudWatch publishing, and prefix-level aggregation for 15 months

## Limitations

- API access requires auth; static website hosting doesn't support HTTPS natively
- Use CloudFront + S3 for HTTPS-enabled static hosting (see [content-delivery.md](../02-networking/content-delivery.md))
